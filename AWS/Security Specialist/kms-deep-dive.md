## Mental model: what KMS actually is

**KMS = a key custody and authorization service**, not a bulk encryption service.

It exists to do three things:
1. **Hold key material** (in HSMs, customer-controlled or AWS-controlled)
2. **Authorize cryptographic operations** (via key policies, IAM, grants)
3. **Provide audit trail** (every KMS operation logs to CloudTrail)

It does NOT (cannot) encrypt large data directly. KMS has a **4 KB input limit** for `Encrypt` operations. For anything larger, KMS gives you a **data encryption key (DEK)** and you do the encryption locally.

This single fact drives ~50% of exam KMS questions:
- "Encrypt large S3 object" → NOT `kms:Encrypt`, use `kms:GenerateDataKey` (envelope)
- "Encrypt small secret" → `kms:Encrypt` is fine
- "Client-side encryption library" → uses `kms:GenerateDataKey`, NOT `kms:Encrypt`

## Glossary (memorize these terms)

| Term | Definition |
|---|---|
| **CMK** (deprecated) | Customer Master Key — old name, replaced by "KMS key" |
| **KMS key** | The logical AWS resource (has an ID, ARN, alias) |
| **Key material** | The actual cryptographic bytes used for encryption |
| **DEK** (data key) | A symmetric key generated by KMS for envelope encryption; KMS never stores DEKs |
| **EDK** (encrypted data key) | The DEK after being wrapped (encrypted) by a CMK |
| **Key policy** | Resource-based policy attached to the KMS key (THE primary access control) |
| **Grant** | Programmatic delegation of key usage to a principal (alternative to key policy) |
| **Alias** | Friendly pointer to a key (e.g., `alias/myProd`) — can be re-pointed |
| **Key store** | Where key material is held (default KMS / CloudHSM / external HSM) |
| **Envelope encryption** | Pattern: KMS wraps a DEK, DEK encrypts the data, store both together |
| **Encryption context** | Additional Authenticated Data (AAD) for integrity verification — NOT key generation |
| **Multi-Region key** | Set of related KMS keys in different regions with same key ID & material |

## Key types matrix (the foundational table)

There are 3 ORTHOGONAL classifications:

### 1. By ownership
| Type | Who creates? | Who manages? | Customer can use directly? |
|---|---|---|---|
| **AWS-owned** | AWS | AWS | NO — invisible to customer |
| **AWS-managed** (`aws/<service>`) | AWS (on first use of a service) | AWS | YES — but cannot delete or change policy |
| **Customer-managed** | Customer | Customer | YES — full control |

### 2. By key material origin
| Origin | Auto-rotation? | Immediate delete? | Key store |
|---|---|---|---|
| **AWS-generated** (default) | ✅ Optional (90-2560 days) | ❌ No (7-30 day wait) | Default OR Custom Key Store |
| **Imported (BYOK)** | ❌ NEVER (manual only) | ✅ YES (via `DeleteImportedKeyMaterial`) | Default ONLY |
| **Custom Key Store (CloudHSM)** | ❌ No (you manage in HSM) | Depends on CloudHSM cluster | Custom Key Store |
| **External Key Store (XKS)** | ❌ No (you manage externally) | Depends on external HSM | External Key Store |

### 3. By cryptographic type
| Type | Auto-rotation? | Use cases |
|---|---|---|
| **Symmetric (default, AES-256)** | ✅ Yes (only this type can auto-rotate) | Encryption, envelope encryption, MAC |
| **Asymmetric RSA** | ❌ No | Sign/Verify, Encrypt/Decrypt with public key |
| **Asymmetric ECC** | ❌ No | Sign/Verify (faster than RSA, smaller keys) |
| **HMAC** | ❌ No | Message authentication codes |

**The critical takeaway**: auto-rotation works ONLY for **symmetric, AWS-generated, in default key store**. Every other combination requires MANUAL rotation.

## The rotation rules (most-missed pattern)

### Auto-rotation eligibility checklist
For `EnableKeyRotation` to work, the key must be ALL of:
- ✅ Symmetric (not asymmetric, not HMAC)
- ✅ AWS-generated material (not imported)
- ✅ In default key store (not Custom Key Store, not XKS)
- ✅ Customer-managed (AWS-managed keys rotate automatically without your input; AWS-owned are invisible)

If ANY of these fails, `EnableKeyRotation` returns an error or is silently unavailable.

### Manual rotation pattern (Q1 — you got this right)
The pattern works for ALL key types, even imported:
1. Create a NEW KMS key
2. (For imported) Import key material into the new key
3. **Re-point the alias** from the old key to the new key
4. Applications using the alias automatically use the new key
5. Keep the old key active (for decrypting historical data)
6. Optional: schedule old key for deletion AFTER all data is re-encrypted

### Rotation cadence
- Auto-rotation: configurable **90 to 2560 days** (default is 365 days)
- Rotation rotates the **backing material**, not the key ID/ARN
- Old material is retained internally for decryption
- **Existing ciphertext is NOT re-encrypted** — each ciphertext references the exact material version that wrapped it

### Deletion windows
| Key type | Deletion behavior |
|---|---|
| AWS-generated symmetric | Schedule for 7-30 day waiting period (default 30) |
| Asymmetric | Same: 7-30 day waiting period |
| **Imported material** | Can use `DeleteImportedKeyMaterial` for **immediate delete** of material (the key shell remains, can re-import same material) |
| AWS-managed (`aws/*`) | Cannot be deleted by customer |

**Reflex**: "delete in under 7 days" → ONLY imported material allows this.

### Cancel deletion (Q14 — you got this right)
- During the 7-30 day waiting period, key state is `PendingDeletion`
- `CancelKeyDeletion` API restores the key to `Disabled` state
- **After the waiting period ends, the key is permanently gone**
- AWS Support **CANNOT** recover a deleted key (don't believe options that claim this)

## Key material options — the imported material gotcha

### Default key store (AWS-managed HSMs)
- AWS-generated material OR imported (BYOK)
- Auto-rotation works for AWS-generated only
- Immediate delete works for imported only

### Custom Key Store (CloudHSM-backed)
- Material is in YOUR CloudHSM cluster (inside AWS)
- KMS API still works (S3 SSE-KMS, etc.)
- **CANNOT import material** — keys must be generated INSIDE the HSM
- FIPS 140-2 Level 3

### External Key Store (XKS)
- Material is in YOUR HSM OUTSIDE AWS
- KMS API still works
- **CANNOT import material** to AWS (the material doesn't live in AWS at all)
- Latency higher (cross-region/cross-cloud calls)

### Imported key material rules (Q33 reinforcement)
1. Key material is **permanently bound** to the key ID on import — cannot change later
2. Can RE-import the SAME material (e.g., to extend material expiration)
3. Cannot import to a Custom Key Store or XKS
4. Cannot enable auto-rotation on imported material
5. The KMS key has both a key ID AND key material expiration date (optional)
6. After material deletion (immediate via API), key state becomes `PendingImport` until you re-import

## KMS API actions catalog (memorize each)

### Symmetric encryption operations
| Action | Returns | Input limit | Use case |
|---|---|---|---|
| `Encrypt` | Ciphertext | **4 KB plaintext** | Small secrets (passwords, tokens) |
| `Decrypt` | Plaintext | (4 KB ciphertext) | Universal decrypt — handles both `Encrypt` and `GenerateDataKey` outputs |
| `GenerateDataKey` | Plaintext DEK + encrypted DEK | N/A | **Envelope encryption** (S3 SSE-KMS, client-side SDKs, files >4 KB) |
| `GenerateDataKeyWithoutPlaintext` | Encrypted DEK only | N/A | Pre-provision DEKs for offline encryption later |
| `GenerateDataKeyPair` | Asymmetric key pair (plaintext + encrypted private) | N/A | Generate ephemeral key pairs for signing/encryption |
| `GenerateDataKeyPairWithoutPlaintext` | Encrypted private key only | N/A | Pre-provision asymmetric key pairs |
| `ReEncrypt` | Re-wrapped ciphertext | (4 KB ciphertext) | Migrate to new CMK without exposing plaintext |
| `GenerateRandom` | Random bytes | N/A | Get cryptographically random bytes (for nonces, etc.) |
| `GenerateMac` | MAC | (4 KB message) | HMAC keys only |
| `VerifyMac` | Boolean | (4 KB message + MAC) | HMAC keys only |

### Asymmetric operations
| Action | Use case |
|---|---|
| `GetPublicKey` | Download public half of asymmetric key (for offline encryption or verification) |
| `Sign` | Sign a digest with private key (returns signature) |
| `Verify` | Verify a signature with public key (returns boolean) |
| `Encrypt` (on asymmetric) | Encrypt with public key — but typically you'd use GetPublicKey + offline RSA encryption |
| `Decrypt` (on asymmetric) | Decrypt with private key — private never leaves KMS |

### Key lifecycle operations
| Action | Use case |
|---|---|
| `CreateKey` | Create a new KMS key |
| `ScheduleKeyDeletion` | Start 7-30 day deletion countdown |
| `CancelKeyDeletion` | Stop deletion countdown (only works in `PendingDeletion` state) |
| `EnableKey` / `DisableKey` | Toggle key state (cryptographic operations fail when disabled) |
| `EnableKeyRotation` / `DisableKeyRotation` | Toggle auto-rotation (symmetric AWS-generated only) |
| `RotateKeyOnDemand` | Manually trigger rotation NOW (new feature, 2023+) |
| `GetKeyRotationStatus` | Check if auto-rotation is enabled |

### Alias operations
| Action | Use case |
|---|---|
| `CreateAlias` | Bind a name like `alias/myProd` to a key ID |
| `UpdateAlias` | Re-point an alias to a different key (manual rotation pattern!) |
| `DeleteAlias` | Remove an alias |
| `ListAliases` | List all aliases in account/region |

### Policy & grant operations
| Action | Use case |
|---|---|
| `PutKeyPolicy` | Replace the key policy on a key |
| `GetKeyPolicy` | Read the key policy |
| **`CreateGrant`** | Delegate temporary key usage to a principal (services like EC2 use this for EBS) |
| `ListGrants` | List active grants on a key |
| `RevokeGrant` | Revoke a grant by ID |
| `RetireGrant` | Retire (delete) a grant by token |

### Imported material operations
| Action | Use case |
|---|---|
| `GetParametersForImport` | Get wrapping key + import token (one-time use) |
| `ImportKeyMaterial` | Upload wrapped key material |
| `DeleteImportedKeyMaterial` | **Immediate delete** of imported material (key shell remains) |

### Multi-Region key operations
| Action | Use case |
|---|---|
| `ReplicateKey` | Create a replica of a multi-Region key in another region |
| `UpdatePrimaryRegion` | Change which region holds the primary multi-Region key |

### Made-up actions to recognize (NEVER pick these)
- ❌ `kms:GetDataKey` — doesn't exist (it's `GenerateDataKey`)
- ❌ `kms:CreateDataKey` — doesn't exist
- ❌ `kms:WrapKey` — doesn't exist (use `Encrypt` or `GenerateDataKeyWithoutPlaintext`)
- ❌ `kms:UnwrapKey` — doesn't exist (use `Decrypt`)
- ❌ `kms:AssociateKeyMaterial` — doesn't exist
- ❌ `kms:UpdateKeyMaterial` — doesn't exist (material is permanently bound on import)

## KMS condition keys catalog

Condition keys narrow when a permission applies. Critical for least-privilege key policies.

| Condition key | What it checks | Common use |
|---|---|---|
| `kms:CallerAccount` | The AWS account of the calling principal | Restrict cross-account access |
| `kms:ViaService` | Which AWS service is calling KMS on behalf of the principal | "This key can only be used through S3" |
| **`kms:GrantIsForAWSResource`** | Whether the CreateGrant is initiated by an AWS service on user's behalf | EC2+EBS pattern (Q55) |
| `kms:GrantOperations` | The list of operations a grant allows | Limit what grants can permit |
| `kms:GranteePrincipal` | The principal that the grant is FOR | Limit who can be the grantee |
| `kms:RetiringPrincipal` | The principal that can retire a grant | Control grant cleanup |
| `kms:GrantConstraintType` | The type of constraint added to a grant | Fine-grained grant control |
| `kms:EncryptionContext:<key>` | A specific encryption context key/value pair | Multi-tenant isolation |
| `kms:EncryptionContextKeys` | The keys (not values) present in encryption context | Require certain context fields |
| `kms:RequestAlias` | The alias used in the request | Differentiate access by alias |
| `kms:ResourceAliases` | All aliases on the key being acted on | Tag-based key control |
| `aws:PrincipalOrgID` | The AWS Organization ID of the caller | Restrict to your org (Q65) |
| `aws:PrincipalIsAWSService` | Whether the caller is an AWS service principal | Differentiate service vs user calls |
| `aws:SourceArn` | ARN of the resource making the call | Restrict to specific source |
| `aws:SourceAccount` | Account of the source resource | Restrict to specific account |

## Key policies vs IAM policies vs grants (the 3-layer authorization model)

### Key policy (primary, REQUIRED)
- Resource-based policy attached to the KMS key itself
- Every key MUST have a key policy
- Default key policy includes a statement granting root full access AND delegating to IAM
- If you remove the root statement → **lockout** (only AWS Support can fix)

**The unique KMS quirk**: unlike most AWS services, root has NO implicit access. Root works ONLY because the default key policy explicitly grants it.

### IAM policy (only works if key policy delegates)
- Identity-based policy attached to user/group/role
- Works ONLY if the key policy includes the statement:
  ```json
  {
    "Effect": "Allow",
    "Principal": { "AWS": "arn:aws:iam::ACCOUNT:root" },
    "Action": "kms:*",
    "Resource": "*"
  }
  ```
- This statement says "delegate to IAM" — without it, IAM policies on the same account can't grant KMS access
- The default key policy includes this delegation

### Grants (programmatic temporary delegation)
- Created via `kms:CreateGrant` API call
- Authorize specific principals for specific operations
- Used heavily by AWS services that need temporary key access (EC2 for EBS encryption, ASG for launching encrypted instances, RDS for snapshots)
- Can be limited by constraints: encryption context, granted operations
- Can be revoked (`RevokeGrant`) or retired (`RetireGrant`)
- **Cannot grant to AWS service principals directly** — grantees must be account/user/role

### When to use which
| Scenario | Use |
|---|---|
| Static permission for an account | Key policy |
| Static permission for a user/role | IAM policy (if key policy delegates) |
| Cross-account access | Key policy (must allow other account) + IAM in other account |
| **AWS service needs temporary access** (EC2 launching encrypted EBS) | **Grant** (created by user with `kms:CreateGrant` permission) |
| Time-limited / scoped permission | Grant with constraints |

## Envelope encryption (the pattern that drives most KMS questions)

### Why envelope encryption exists
- KMS has a 4 KB input limit on `Encrypt`
- Files are usually MUCH bigger
- Calling KMS for every byte would be slow + expensive

### The pattern
```
ENCRYPTING SIDE:
1. Client calls kms:GenerateDataKey(KeyId=CMK)
   → KMS returns: 
     - PlaintextDataKey (256-bit AES key)
     - EncryptedDataKey (the same key wrapped with CMK)
2. Client uses PlaintextDataKey to AES-encrypt the file locally
3. Client throws away PlaintextDataKey from memory
4. Client stores:
   - The encrypted file
   - EncryptedDataKey (alongside, in metadata, or separately)

DECRYPTING SIDE:
1. Client retrieves encrypted file + EncryptedDataKey
2. Client calls kms:Decrypt(CiphertextBlob=EncryptedDataKey)
   → KMS returns PlaintextDataKey
3. Client uses PlaintextDataKey to AES-decrypt the file locally
4. Client throws away PlaintextDataKey
```

### Why kms:Encrypt is NOT what client-side SDKs use
The exam question (Q15): "client-side encryption library, what KMS action is missing from the policy?"
- ❌ `kms:Encrypt` — only handles ≤4 KB
- ✅ `kms:GenerateDataKey` — envelope encryption pattern, supports unlimited data size

### Libraries that use envelope encryption (memorize)
| Library | Calls |
|---|---|
| **AWS Encryption SDK** | `kms:GenerateDataKey` + `kms:Decrypt` |
| **S3 Encryption Client** | `kms:GenerateDataKey` + `kms:Decrypt` |
| **AWS Database Encryption SDK (DynamoDB)** | `kms:GenerateDataKey` + `kms:Decrypt` |
| **Server-side SSE-KMS (S3, RDS, EBS)** | `kms:GenerateDataKey` + `kms:Decrypt` (server does the dance) |

### Server-side vs client-side
- **Server-side (SSE-KMS)**: AWS service does the envelope dance for you. You just configure the CMK.
- **Client-side**: YOUR code does the envelope dance using one of the SDKs above.

In both cases, KMS sees `GenerateDataKey` + `Decrypt`, never `Encrypt` of bulk data.

## Cross-account KMS patterns

### Same account (default)
- Key policy includes root delegation statement
- IAM policy on user/role grants `kms:Decrypt` etc.
- No additional setup needed

### Cross-account (key in Account A, user in Account B)
**REQUIRED on both sides:**
1. **Account A** (key owner): key policy must explicitly allow Account B's principal
   ```json
   {
     "Effect": "Allow",
     "Principal": { "AWS": "arn:aws:iam::ACCOUNT_B:root" },
     "Action": ["kms:Decrypt", "kms:Encrypt", "kms:GenerateDataKey"],
     "Resource": "*"
   }
   ```
2. **Account B** (user side): IAM policy on the principal grants matching KMS actions on the key ARN

**Both must allow.** Missing either side = AccessDenied.

### Cross-account for AWS services (Q58 pattern)
Example: ASG in Account B launches EC2 instances with EBS encrypted by CMK in Account A.

**Required setup:**
1. **Account A key policy** allows Account B to use the key
2. **Account B grant**: Create a `kms:CreateGrant` for the Auto Scaling service-linked role, with `kms:GrantIsForAWSResource: true` condition

This is the textbook ASG + encrypted EBS pattern. Sharing snapshots is NOT sufficient — the service-linked role needs grant permission.

### Resource sharing rules
- **EBS snapshots**: can ONLY share encrypted snapshots if encrypted with customer-managed CMK (not default `aws/ebs`)
- **AMIs**: same — must be customer-managed CMK
- **RDS snapshots**: same — must be customer-managed CMK (Q20)
- **S3 objects**: same — encrypted with `aws/s3` cannot be shared cross-account easily

**Recurring exam trap**: "share snapshot encrypted with default KMS key" → construction error. Default keys cannot be shared.

## Multi-Region keys (the Q33 pattern)

### What they are
A set of related KMS keys in different regions with:
- Same key ID (e.g., `mrk-1234abcd...`)
- Same key material
- Same key policy (initially; can diverge)
- Independent rotation schedules (each region's replica rotates separately)
- ARNs differ by region

### Why they exist
- Encrypt in Region A, decrypt in Region B without cross-region calls or re-encryption
- Disaster recovery patterns
- Compliance scenarios where data must stay in-region

### How to create
1. `CreateKey` with `MultiRegion: true` in primary region → primary multi-Region key
2. `ReplicateKey` to additional regions → replica multi-Region keys
3. `UpdatePrimaryRegion` to change which region holds the primary (e.g., during failover)

### Critical limitations
- **CANNOT convert a single-Region key to multi-Region** (Q33 trap)
- **CANNOT convert a multi-Region key to single-Region**
- **CANNOT replicate a multi-Region key between AWS partitions** (e.g., commercial ↔ GovCloud)
- **Amazon S3 currently treats multi-Region keys as single-Region** — must replicate data separately

### The Q33 pattern (memorize)
"Existing data encrypted with single-region key, want to replicate to second region with same key in both regions"

**Correct approach:**
1. Create a NEW S3 bucket in primary region
2. Enable SSE-KMS encryption on the NEW bucket using a multi-Region KMS key (created from scratch)
3. **Copy the existing data** from old bucket to new bucket (this re-encrypts with new multi-Region key)
4. Set up S3 replication from new bucket to second region's bucket

**Why other approaches fail:**
- Converting existing single-Region key to multi-Region: NOT POSSIBLE
- Sharing the existing key across regions: NOT POSSIBLE (single-Region keys can't be shared)
- Using Lambda to copy with re-encryption: works but high operational overhead, daily frequency loses data

## Service-specific KMS patterns

### EC2 + EBS encrypted (Q55 pattern)
**Scenario**: IAM user with full EC2 permissions can't start an instance with encrypted EBS volumes.

**Why**: EC2 needs to decrypt the EBS volume to launch the instance. EC2 doesn't have permission directly — it needs the USER to create a grant delegating decrypt to EC2.

**Fix**:
```json
{
  "Effect": "Allow",
  "Action": "kms:CreateGrant",
  "Resource": "arn:aws:kms:REGION:ACCOUNT:key/KEY_ID",
  "Condition": {
    "Bool": { "kms:GrantIsForAWSResource": true }
  }
}
```

**Why `GrantIsForAWSResource: true`**: limits the user to creating grants ONLY when an AWS service initiates the call. Prevents the user from creating arbitrary grants to other principals.

**This pattern also applies to**: ASG launching encrypted instances, RDS launching encrypted DBs, snapshots being decrypted by snapshots operations.

### ASG + encrypted EBS (Q58 pattern)
**Scenario**: ASG in Account B needs to launch instances with EBS encrypted by CMK in Account A.

**Required setup (BOTH sides):**
1. **Account A** (key owner): update key policy to allow Account B (`aws:PrincipalAccount = B`)
2. **Account B** (launcher): create a KMS grant for the Auto Scaling service-linked role on the key

The grant authorizes the service-linked role specifically to use the key during launches.

### RDS encryption
- Must be set **at DB instance creation time** — cannot enable encryption on existing unencrypted RDS
- To add encryption: snapshot → copy snapshot with encryption → restore from encrypted snapshot
- Snapshots inherit encryption status of source DB

### S3 SSE-KMS
- Configure bucket default encryption with a CMK
- S3 calls `GenerateDataKey` + `Decrypt` on your behalf
- Each object gets a unique DEK (automatically — you don't manage this)
- **Bucket Key** feature reduces KMS calls by ~99% via cached DEKs (cost savings)
- DSSE-KMS = dual-layer encryption (two layers of envelope encryption for high-security needs)

### Lambda environment variables
- Encrypted at rest using KMS by default (`aws/lambda`)
- Can use customer-managed CMK
- Function needs `kms:Decrypt` on the CMK (via execution role)
- Function needs `kms:Encrypt` to update env variables

### Secrets Manager (Q34 reinforcement)
- Each secret encrypted with a CMK (AWS-managed `aws/secretsmanager` by default)
- Cross-region replication automatically uses an AWS-managed key in the destination region
- For multi-region with customer-managed keys: use multi-Region keys

### Parameter Store SecureString
- Encrypted with `aws/ssm` by default OR customer-managed CMK
- Reading requires `kms:Decrypt` on the CMK
- **Common error**: instance role has Parameter Store permissions but not KMS Decrypt

## Question pattern recognition (drill these)

### Pattern 1: "What action enables encryption of large data?"
**Trigger words**: "client-side encryption," "large file," "S3 object," "envelope encryption," "AWS Encryption SDK"

**Answer**: `kms:GenerateDataKey` (NOT `kms:Encrypt`)

### Pattern 2: "Why can't user start EC2 with encrypted EBS?"
**Trigger words**: "EC2 instance with encrypted EBS," "client error on launch," "instance goes to Pending then Stopped"

**Answer**: User needs `kms:CreateGrant` on the CMK + condition `kms:GrantIsForAWSResource: true`

### Pattern 3: "Recover deleted KMS key"
**Trigger words**: "deleted KMS key," "pending deletion," "recover"

**Answer**: 
- During 7-30 day window: `CancelKeyDeletion`
- After window: GONE FOREVER (no recovery, not even AWS Support)

### Pattern 4: "Mandate MFA for sensitive S3 access"
**Trigger words**: "MFA," "S3 access," "deny without MFA"

**Answer**: `Deny + BoolIfExists + aws:MultiFactorAuthPresent: false`
- Covers temp creds without MFA AND long-term access keys (which don't have the key)

### Pattern 5: "Multi-region key for replication"
**Trigger words**: "encrypt in one region, decrypt in another," "DR," "disaster recovery"

**Answer**: 
- Create NEW multi-Region key from scratch (can't convert existing single-Region key)
- Replicate to other regions with `ReplicateKey`
- For S3: create NEW bucket with multi-Region key, copy existing data

### Pattern 6: "Imported material rotation"
**Trigger words**: "imported key material," "BYOK," "rotate annually"

**Answer**: Manual rotation pattern:
1. Create new KMS key
2. Import new material into new key
3. Re-point alias from old key to new key
4. Apps using alias automatically use new key

### Pattern 7: "Cross-account snapshot/AMI sharing"
**Trigger words**: "share encrypted snapshot/AMI/RDS snapshot with another account"

**Answer**: Customer-managed CMK + share both snapshot AND key with target account

### Pattern 8: "Root user locked out of KMS key"
**Trigger words**: "root user can't access," "key policy issue"

**Answer**: Root has no implicit KMS access. Default key policy includes a statement granting root — if deleted, only AWS Support can fix. **For exam: this is a one-way trip; recovery is impossible without AWS Support intervention.**

### Pattern 9: "Restrict key to my organization only"
**Trigger words**: "AWS Organization," "only my org," "centralized control"

**Answer**: Key policy with condition `aws:PrincipalOrgID = o-xxxxxxxx`

### Pattern 10: "ASG cross-account encrypted instance launch"
**Trigger words**: "Auto Scaling," "cross-account," "encrypted EBS," "service-linked role"

**Answer**: 
1. Key owner account: update key policy to allow launcher account
2. Launcher account: create grant for ASG service-linked role with `GrantIsForAWSResource: true`

## Final exam-day KMS quick reference

### When to pick each KMS action
| Need | Action |
|---|---|
| Encrypt small (< 4 KB) | `Encrypt` |
| Encrypt large (file, object, anything ≥ 4 KB) | `GenerateDataKey` (envelope) |
| Decrypt anything KMS-encrypted | `Decrypt` |
| Pre-provision encrypted DEK without using it now | `GenerateDataKeyWithoutPlaintext` |
| Delegate temporary key use to AWS service | `CreateGrant` (+ `GrantIsForAWSResource` condition) |
| Sign data with private key | `Sign` (asymmetric only) |
| Verify signature | `Verify` (asymmetric only) |
| Re-wrap to new CMK without exposing plaintext | `ReEncrypt` |
| Generate random bytes | `GenerateRandom` |
| View key metadata (key state, type, etc.) | `DescribeKey` |
| Read key policy | `GetKeyPolicy` |
| Download asymmetric public key | `GetPublicKey` |
| HMAC message | `GenerateMac` (HMAC keys only) |

### When to choose each key material option
| Need | Option |
|---|---|
| Most common, AWS handles HSMs | Default key store, AWS-generated symmetric |
| Bring your own key (BYOK) | Default key store, imported material |
| You control the HSM (in AWS) | Custom Key Store (CloudHSM) |
| You control the HSM (outside AWS) | External Key Store (XKS) |
| Asymmetric crypto (sign/verify, public-key encrypt) | AWS-generated asymmetric (RSA or ECC) |
| Message authentication | HMAC key |
| Multi-region encryption | Multi-Region key (NEW key, cannot convert existing) |

### Key policy must-haves for typical scenarios
| Scenario | Policy fragment |
|---|---|
| Default account access | Root statement + IAM delegation |
| Restrict to AWS service caller | `kms:ViaService` condition |
| Restrict to your AWS Org | `aws:PrincipalOrgID` condition |
| Allow EC2 launch grants | `kms:CreateGrant` + `kms:GrantIsForAWSResource: true` |
| Cross-account access | Other account as Principal + matching IAM in other account |
